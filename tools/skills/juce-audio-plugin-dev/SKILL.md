# Разработка аудиоплагинов на JUCE

Доводить согласованное изменение до проверенной сборки, сохраняя поведение старых проектов DAW. Пути, версии JUCE, команды сборки и разрешения брать из текущего проекта; опыт одного плагина не задаёт требования для остальных.

## Контекст и ожидаемое поведение

Перед изменениями прочитать инструкции репозитория, README, актуальный план и документ решений, если они есть. Проверить рабочее дерево и используемые конфигурации сборки. Уточнить смысл изменения по существующим параметрам, DSP и тестам, а не только по подписям GUI.

Для неоднозначных музыкальных требований описать наблюдаемое поведение: какой сигнал запускает обработку, что меняется во времени, какие ручки влияют на результат. Например, Attack обычно задаёт скорость нарастания подавления; задержка начала — отдельное решение. Конкретное значение определяется архитектурой плагина. При сравнении с аналогами обращаться к официальным руководствам; не копировать семантику без учёта собственной обработки.

## DSP и параметры

- Не вводить в аудиоколбэк аллокации, блокирующие синхронизации, ввод-вывод или ожидания. Буферы готовить вне обработки; учитывать фактический размер блока и смену sample rate. Проверять используемые атомарные типы на подходящие для целевой платформы гарантии.
- Сглаживать изменения там, где скачок вызывает щелчок или нежелательный переход. Задавать время в физических единицах, учитывать sample rate, reset и повторный триггер. Не сглаживать все параметры одинаково: дискретные режимы и временная геометрия требуют собственного перехода.
- Рассматривать mono/stereo и AUX отдельно. Сумма L/R может отменить противофазный сигнал. Выбор stereo linking детектора, Peak и RMS должен соответствовать назначению; не менять его случайно вместе с GUI.
- Для кривой обработки держать одну модель геометрии и интерполяции для DSP и GUI. Определить пределы точек, разрешённые пересечения, конечное значение и повторный запуск. Отображать эффективные ограничения ручек без скрытой записи автоматизации при открытии редактора.
- Для синхронизации с хостом определить поведение при остановке, отсутствии BPM/PPQ, перемотке, loop, автоматизации темпа и offline render. Отключённый AUX и подключённый AUX без сигнала могут иметь разный смысл; это продуктовое решение, а не автоматический fallback.

Сохранять ID, порядок и диапазоны параметров, идентификаторы форматов и схему состояния, насколько требует совместимость. Изменение смысла или диапазона документировать и проверять миграцией старых состояний. Миграция состояния не исправляет внешние огибающие DAW, сохранённые в нормализованном виде. Не устранять эту проблему молча переименованием старого параметра.

Для новых опциональных режимов сохранять фактическое поведение старых состояний:
отсутствующий параметр не всегда означает новый default OFF. Если раньше обработка
была постоянной, миграция должна включить её явно; последующий пользовательский
выбор сохраняется. Проверять оба порядка restore/prepare: хост может восстановить
состояние после prepareToPlay, до первого реального аудиоблока.

## GUI, история и измерители

Передавать в GUI согласованные snapshots с понятным владением данными. Не читать playhead из GUI-потока. Для истории проверить публикацию завершённых записей, reset, переполнение кольца и чтение во время перезаписи; отдельные атомарные поля сами по себе не гарантируют целостность кадра.

Различать удерживаемый кадр по триггеру и непрерывный осциллоскоп. Выбирать длительность окна и ёмкость по максимальному поддерживаемому sample rate с запасом. При уменьшении числа точек сохранять значимые пики; синхронные аудио и GR рисовать по одной временной шкале. Если метрики агрегируются независимо, не терять пик GR из-за выбора пика аудио.

Определить точки измерения относительно input gain, обработки, dry/wet и output gain. Для общего stereo RMS можно использовать среднюю мощность каналов; mono не делить пополам. Sample Peak, True Peak, RMS и LUFS обозначать по фактическому алгоритму. Баллистику дисплея отделять от управляющего DSP; числа и бары брать из одного кадра. Проверять ресайз, читаемость, единицы и превышение диапазона измерителей.

У биполярных ручек различать ноль, направление и знак значения; проверять
читаемость обозначений вне/внутри ручки на минимальном размере, не меняя
host-нормализацию ради визуального центрирования.

## Лимитеры и true peak

Для независимой проверки true peak, истории выхода/GR и нескольких ступеней
обработки читать [references/limiter-validation.md](references/limiter-validation.md).
Oversampling сам по себе не доказывает соблюдение выходного true-peak потолка.

## Проверка и завершение

Выбирать проверки по риску изменения, используя существующую инфраструктуру. Для DSP полезны аналитические сигналы и сравнение результата по samples, а не тесты, повторяющие реализацию. Для изменения только оформления достаточно подходящей визуальной проверки.

Для затронутого поведения проверить релевантные сочетания частот дискретизации и блоков, mono/stereo, противофазу и сигнал в одном канале, тишину и reset. При изменениях параметров проверить старые состояния, round-trip, автоматизацию и открытие GUI без изменения параметров. Для истории проверить начальное заполнение, переполнение и обмен между потоками. При необходимости провести отдельный аудит гонок и аллокаций; успешный функциональный тест не доказывает их отсутствие.

Сначала выполнить относящиеся к изменению проверки, затем собрать нужные форматы командами проекта. Для GUI просмотреть минимальный и увеличенный размеры; screenshot не подтверждает качество анимации и звучания. Не добавлять lookahead или oversampling без задачи либо измеренной потребности; учитывать задержку и её сообщение хосту при таких изменениях.

Устанавливать сборку только в рамках разрешений пользователя. Skill не даёт разрешения запускать DAW, заменять установленный плагин, коммитить или публиковать. Если установка разрешена, проверить результат копирования. Обновить проектный план и решения, если они ведутся.

В завершении сообщить, что изменилось, какие проверки прошли, установлена ли сборка и какие конкретные сценарии нужно проверить в DAW. Разделять автоматическую валидацию, просмотр GUI и прослушивание. Для выпуска по согласованному объёму проверять нужные хосты, несколько экземпляров, сохранение/восстановление проекта и offline render; не объявлять коммерческую готовность на основании одной сборки.
